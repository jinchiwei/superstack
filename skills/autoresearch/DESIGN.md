## Problem Statement

User runs long autonomous research loops (multi-day, in tmux) by giving a verbal recipe at session start: "iterate over architectures, input modes, loss functions; log everything; commit and push; record to research-log; don't ask me questions; I'll be back in a few days." The verbal recipe drifts, isn't reproducible, and depends on the user remembering to say all the right things. Memory-only mechanisms (a feedback memory like "always log to research-log") are unreliable for multi-day autonomous behavior — context compaction over long runs erodes the directive.

Goal: encode the verbal recipe as a skill so the invariants are deterministic, the loop self-paces, the research-log push happens structurally, and the user invokes `/autoresearch <scope>` once and walks away.

## What Makes This Cool

- **Self-paced via ScheduleWakeup.** User types `/autoresearch <scope>` once. Skill iteration ends with `ScheduleWakeup(prompt="/autoresearch", delaySeconds=N)` to fire itself again. No `/loop` wrapping needed.
- **Plan, then drift.** Initial axes enumerated from the free-text scope and confirmed once at launch. After that, the skill *adaptively replans* each iteration based on accumulated results. The plan is a launch state, not a contract.
- **Agentic code-fix during failures.** When an experiment dies on a Python traceback, the skill attempts an Edit on the failing line, reruns, and only marks the candidate dead after 2-3 fix attempts fail. Lets autoresearch fight through bugs that would otherwise burn half the search budget.
- **One growing log file per session.** Per-iteration appends to a single `YYYY-MM-DD_autoresearch-<scope-slug>.md` entry; PIVOT and meaningful-result blocks are headers within it; final summary appended on termination. Same file, growing live.
- **Setup-agnostic.** Research-log push is optional — auto-detect `~/arcadia/research-log/`; fall back to a local `notes.md` if absent.

## Constraints

- Lives in `~/arcadia/superstack/skills/autoresearch/` — no separate infra.
- Composes with `/loop` if user wants to override pacing (e.g. `/loop 30m /autoresearch`), but does NOT require it.
- Substrate is tmux + Claude Code. Loop lives within ONE Claude Code session via ScheduleWakeup. Not a detached daemon.
- State on disk for cross-session restart if the Claude Code session dies (user re-invokes `/autoresearch` to resume against existing state.json).
- Only ONE blocking interactive prompt allowed in the entire workflow: the plan-confirm at launch. Everything else must be non-blocking.

## Premises (all confirmed in Phase 3)

1. **tmux + Claude Code is the substrate.** ScheduleWakeup keeps the loop alive within one Claude Code session. If the session dies, the loop dies with it; user re-invokes `/autoresearch` against existing state.json to resume.
2. **Agentic code-fix is in scope.** The skill modifies the user's working tree mid-run when fixing experiment bugs. Successful experiments commit cleanly. The working tree mutates between commits.
3. **Judgment-driven log cadence is acceptable.** Per-iteration appends are deterministic. PIVOT markers and meaningful-result promotions inside the file rely on LLM judgment; we accept the drift on soft markers because the live append is reliable enough for widget freshness.
4. **One autoresearch session = one log file.** Each `/autoresearch` invocation creates one growing file for the entire run, even multi-day. New invocation = new file. State.json is the cross-session continuity layer.
5. **research-log push is OPTIONAL.** Skill auto-detects `~/arcadia/research-log/`; if absent, falls back to a local file. No hard dependency.

## Design Decisions

### D1 — Search-space spec: hybrid (free-text + plan-confirm at launch)

User invokes:

```
/autoresearch "iterate over architectures, input modes, loss functions for the FW prediction model. target: val_corr > 0.85"
```

On first invocation for a project (no `state.json`):

1. Skill parses the free-text scope into concrete axes (e.g. `{arch: [unet, transformer, mlp], input: [t1, t2, dwi], loss: [mse, smoothl1, ...]}`) plus a `target_metric` extraction (here: `val_corr > 0.85`).
2. Writes axes + target to `state.json` with `phase: planning`.
3. Shows planned axes inline. Asks ONCE, via AskUserQuestion: "Confirm and launch, edit axes, or cancel?" This is the only blocking prompt — pre-launch, not during the run.
4. On confirmation: sets `phase: running`, picks first candidate experiment from the queue, runs it, replans, calls `ScheduleWakeup(prompt="/autoresearch", delaySeconds=60, reason="next iteration")` and exits.

Subsequent invocations (state.json shows `phase: running`):

- No prompt. Pick next candidate from queue, run, replan based on accumulated results, ScheduleWakeup again.

The plan is a launch state, not a constraint. Adaptive replanning each iteration can add new candidates, deprioritize axes, or pivot to a different approach entirely based on what results so far suggest.

### D2 — Research-log cadence: hybrid one-file-per-session

When `~/arcadia/research-log/` exists and is a git repo:

- On `phase: running` first iteration of the session, create:
  ```
  ~/arcadia/research-log/<top-level>/<project-slug>/YYYY-MM-DD_autoresearch-<scope-slug>.md
  ```
  Header includes: title, blurb (per existing research-log format rules), date, project, status, scope, planned axes, target metric.
- Each subsequent iteration *appends* a 3-5 line iteration block: timestamp, experiment ID, what changed vs prior, result, decision (continue / replan / pivot).
- When state.json marks `pivot: true` (skill judges that the next-move category differs from current), append a `## PIVOT — <reason>` header block.
- When skill judges a result is "meaningful" (notably better than current best, or a surprising negative), append a `## RESULT — <name>` block.
- On termination (target hit / exhausted / STOP / fatal infra error), append a `## Final Summary` block with overall narrative, best-found candidate, what's left.
- After every append: `git pull --rebase origin main && git add . && git commit -m "<self-contained message>" && git push origin main` (per existing research-log convention).

When `~/arcadia/research-log/` absent:

- Use `~/.gstack/projects/<slug>/autoresearch/notes.md` as a local-only narrative log with the same append behavior. No git push.

### D3 — Stop conditions: metric / exhaustion / STOP file

Skill checks at iteration start, in this order:

1. `~/.gstack/projects/<slug>/autoresearch/STOP` exists → finish current iteration, write final summary, exit cleanly. (Created by user via `touch <path>/STOP`.)
2. Target metric (parsed from scope) achieved by current best → final summary, exit.
3. Candidate queue empty after replan AND no new candidates emerged from the last 3 replans → final summary, exit.
4. Else: continue.

### D4 — Failure handling: graduated, biased toward continue

The skill **fights HARD to keep going.** Halts only when truly impossible.

| Error class | Examples | Policy |
|---|---|---|
| **Transient** | OOM, CUDA driver flake, file-lock contention, transient network blip during data download | Retry up to 3× with sensible adjustments (smaller batch, longer timeout, exponential backoff). Mark candidate dead only after all retries exhausted. |
| **Code bug** | Python traceback referring to user code; `AttributeError`, `NameError`, `ValueError` on tensor ops, `TypeError` on arg signatures | **Agentic code-fix attempt.** Skill `git stash`'s, reads the failing line via traceback, attempts a small Edit (fix arg order, add missing import, correct attribute name), reruns. Up to 3 fix attempts. If a fix makes things worse, `git stash pop` to revert before next attempt. Only after 3 failed fix attempts, mark the candidate dead and move on. |
| **Infrastructure** | Disk full, GPU vanished entirely, can't write to filesystem, conda env broken, repo in detached state | Halt loop. Append high-priority `## INFRASTRUCTURE FAILURE — <description>` block to research-log entry (so user gets the alert via the desktop widget). State.json preserves; user resolves the infra issue and re-invokes `/autoresearch` to resume. |

Bias is hard toward "fight through." If a code-fix attempt makes things worse, revert before trying another. Don't accumulate bad fixes.

### D5 — State location

`~/.gstack/projects/<slug>/autoresearch/`:

- `state.json` — search axes, candidate queue, results history, current best, phase, scope_slug, target_metric
- `STOP` — kill switch (user creates with `touch`)
- `QUESTIONS_FOR_USER.md` — mailbox; skill appends timestamped questions when uncertain
- `last-iteration.log` — most recent iteration's stdout/stderr (overwritten each iteration; full history preserved by state.json results array)
- `notes.md` — fallback narrative log when research-log isn't set up

Project autodetect: `git rev-parse --show-toplevel` basename → slug. Falls back to `$(basename "$PWD")` if not in a git repo.

### D6 — Question deferral (mailbox)

When the skill hits a decision it can't confidently make (surprising result, novel error class outside the known taxonomy, plan would deviate substantially from initial axes in a way the user might want to weigh in on):

- Append to `QUESTIONS_FOR_USER.md` with: timestamp, context, the question, **best guess used: <X>**.
- Continue with the best guess. Never block.

User reads on return; can manually edit state.json to override / re-direct.

### D7 — Scope slug parsing

To create the research-log filename, derive a `scope_slug` from the free-text scope:

- LLM generates 2-3 hyphenated words capturing the search domain (e.g. `fw-architecture-sweep`, `loss-function-comparison`, `apoe4-input-modes`).
- Written to state.json as `scope_slug` so it stays stable across iterations of the same session.

## Approaches Considered

### Approach A: Minimal viable loop
Ship just the iteration body — plan, run, replan, ScheduleWakeup, exit. No plan-confirm, no code-fix, no mailbox, single-retry error handling.
- **Effort:** S (one afternoon)
- **Risk:** Low (small surface area)
- **Pros:** Fast to ship; small enough to keep in your head
- **Cons:** Hits the same gaps as the verbal recipe — no plan-confirm catches LLM-hallucinated axes; no code-fix burns search budget on dead branches; no mailbox loses surprising signals
- **Reuses:** Existing skill conventions (gstack project home, ScheduleWakeup primitive)

### Approach B: Full ideal architecture (RECOMMENDED, chosen in Phase 4)
Everything in this design.
- **Effort:** M (~600-1000 lines of skill prose + small bash helpers)
- **Risk:** Med (LLM-driven adaptive replanning + code-fix needs prompt iteration after first real-world runs)
- **Pros:** Every decision lands; one SKILL.md + small bash helpers, no separate infra; ScheduleWakeup self-pacing composes with /loop if pacing override needed
- **Cons:** Largest first PR; LLM behavior tuning is iterative
- **Reuses:** gstack project-home convention, research-log format rules, ScheduleWakeup primitive, AskUserQuestion gating

### Approach C: Daemon (skill as thin client)
Split the loop into a separate Python process; skill submits to / queries the daemon via JSON-RPC.
- **Effort:** L (separate Python service + supervisor + log shipping)
- **Risk:** High (separate infra to maintain)
- **Pros:** Survives Claude Code session crashes (genuine background daemon)
- **Cons:** Splits autoresearch logic across two languages/contexts; user explicitly wanted superstack/skills/, not standalone infra; doesn't match the asked-for shape
- **Reuses:** Nothing existing

## Recommended Approach

**Approach B — Full ideal architecture.** Confirmed in Phase 4.

Rationale:
- Each component (plan-confirm, code-fix, graduated errors, optional research-log push, mailbox, STOP file) addresses a specific gap in the verbal recipe.
- Skill-only implementation matches the asked-for shape — lives in `~/arcadia/superstack/skills/autoresearch/`.
- ScheduleWakeup self-pacing avoids `/loop` dependency while still being compatible with `/loop` for pacing overrides.
- Setup-agnostic research-log handling makes the skill portable across machines.

## Open Questions

These don't block the design but will need calibration during build/early use:

- **Initial axis enumeration prompt quality.** "iterate over architectures, input modes, losses" — how many axes does this actually produce in practice? Will need real runs to calibrate the LLM prompt for axis enumeration. The plan-confirm at launch catches misses, but quality of the auto-plan affects whether you ever need to edit.
- **Code-fix safety.** When the skill edits the user's working tree, do we always `git stash` before attempting and `git stash pop` on failure? The current design says yes. Lock this in /plan-eng-review.
- **Replan budget.** Each iteration includes adaptive replan logic (LLM-driven). What's the rough token budget per iteration? Affects ScheduleWakeup pacing — too eager and we hit rate limits / context overflow. Probably want adaptive `delaySeconds` based on recent iteration cost.
- **Project commit cadence.** Each successful experiment iteration probably commits the project repo (so you can `git log` to see what was tried). What's the commit message format? `WIP: autoresearch <scope_slug> iter <N> [<candidate_id>]`?
- **Detection of "research-log present"** — current design says check for `~/arcadia/research-log/`. Should we also check that the appropriate top-level project dir exists (e.g. `brainlab/`, `wolong/`)? Probably yes — auto-create on first push if missing, or skip with a one-time warning.

## Success Criteria

- User invokes `/autoresearch "<scope>"` once, walks away, and on return finds:
  - A populated research-log entry summarizing what was tried, what worked, what's next.
  - State.json showing the search trajectory.
  - Project repo with clean commit history per successful iteration.
  - A QUESTIONS_FOR_USER.md (possibly empty) listing anything the skill deferred.
- Skill survives transient errors without halting the loop.
- Skill recovers from at least one user-code-bug class without manual intervention (e.g. fixes a typo or arg-order mistake).
- `touch STOP` halts the loop within one iteration of being created (≤ a few minutes typically, depending on iteration runtime).
- Works on a machine WITHOUT research-log set up — just falls back to local notes.
