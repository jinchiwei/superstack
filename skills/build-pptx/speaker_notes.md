# Speaker notes — canonical, comprehensive, didactic

Every `build-pptx` deck SHIPS with speaker notes. Notes are not optional polish — a deck without them is incomplete. The renderer embeds them into the PowerPoint **notes pane** (Presenter View), so the presenter sees them while the audience sees only the slide.

## How (mechanics)

Put the notes for a slide in its sidecar entry under `params["notes"]` (a plain string). `render.py` writes it to that slide's notes pane automatically — for content slides AND section-dividers. No other wiring needed.

```json
{ "kind": "freeform", "params": {
    "title": "...", "code": "...", "_provenance": "agent",
    "notes": "What this slide shows, what to SAY, the key numbers, the transition." } }
```

Write `notes` as free-flowing paragraph(s) — **do NOT prefix your own headline line.** `render.py` automatically prepends the slide's own descriptive title (`params['title']`, or a divider's `label`) as the notes' first line. The presenter-handout PDF (`notes_pdf.py`) renders that first line as the **Geist-Mono-bold headline** ("Slide N — <title>") and your full paragraph below as **regular Geist-sans body**. So the handout always gets a clean bold title without you formatting one, and the body stays readable prose (not all-bold-monospace). The prepend is idempotent — it won't double-add if the notes already start with the title.

(For a deck you've already rendered, you can also post-stamp notes with python-pptx via `slide.notes_slide.notes_text_frame.text` — but the sidecar `params['notes']` path is canonical and survives re-renders.)

## What good notes ARE — didactic, not a teleprompter

Write notes that let someone who is **a little lost** present the slide confidently. For each content slide, cover:

1. **What the slide shows** — name the figure/number/table and what the audience is looking at.
2. **What to SAY, in plain language** — explain the concept from scratch, as if to a smart person outside the field. Define every term the first time (one clause is enough). If the slide has a chart type the audience may not know (e.g. a forest plot), teach how to read it — once.
3. **The key numbers, spoken** — translate stats into intuition ("+23pp" → "about 23 more per 100"; "AUC 0.74" → "promising, not yet clinic-ready").
4. **The transition** — the one sentence that carries into the next slide.
5. **Anticipated questions** (where relevant) — the obvious pushback and a one-line answer.

Length: a solid paragraph per content slide (≈3–7 sentences). Dividers get one transition sentence. Cover/closing get a short framing line. Calibrate total to the talk length (≈60–120s of speaking per content slide for an hour talk).

## What good notes are NOT

- Not a re-print of the on-slide bullets (the slide already says those).
- Not jargon the presenter would have to look up — notes should be MORE plain-spoken than the slide, not less.
- Not empty / "TODO" / one-liners on a content slide.

## Default ON

Generate notes for **every** deck by default — lab talks, conference talks, autoresearch reports, internal readouts. Especially for cold-audience talks (pairs with [`intro_figures.md`](intro_figures.md) and [`bespoke_design.md`](bespoke_design.md)). If the user says "no notes," skip — otherwise include them.

A non-fatal build warning lists content slides missing `params['notes']` so gaps are visible; fill them before delivering.

## Presenter-handout PDF (canonical second output)

Whenever a deck has notes, `build.py` also emits **`<output>_notes.pdf`** — one landscape page per slide: the slide image on top (so every figure/image on the slide is included automatically) and that slide's full notes below. This is the printable/readable script to rehearse from. It's generated by default; it skips gracefully (with a message, never an error) when there are no notes or no rasterizer (LibreOffice + pdftoppm). Disable with `--no-notes-pdf`. Implementation: `notes_pdf.py` (`build_notes_pdf`), reusing `qa.render_to_images`.
